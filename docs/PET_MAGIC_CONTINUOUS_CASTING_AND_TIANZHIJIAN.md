# 魔法系宠物连续施法与方士天之箭

本文记录《什么什么大冒险2》2.101 客户端上的实测和仓库实现，供后续练级脚本复用。适用场景是带队刷图：队长承担必要职责，魔法系宠物用烈焰爆发等群体法术快速清怪。文中区分了用户实测、抓包/代码证据和仍待确认的推断；蓄力增长速度、服务器规则及天赋真实概率都可能随角色和服务端变化。

## 结论速查

- 宠物只有在战斗中、存活、学会目标魔法、MP 足够且有有效目标时，才应尝试施法。蓄力点（战斗状态中的 `SP`）大于 0 是当前刷怪循环采用的施法门槛。
- 正常施法通常会消耗蓄力点。若宠物“完美施法”天赋触发，施法结束后可能不扣点；此时不能空等下一点，应该在确认上一次行动结束后，立刻用仍剩余的蓄力点再次施法。2→1 也要立即再施法，不把剩余 1 点存起来。
- 发出命令后必须等宠物行动结束事件，或观察到 SP 变化，再判断能否发下一条。若行动仍未确认结束，不要盲目重发同一指令，以免重复命令、覆盖行动或造成异常节奏。
- 救倒地队员优先级高于宠物输出：队长执行复活时，宠物本轮改为防御，不能抢先烈焰爆发清场导致战斗结束、复活来不及生效。
- 实测的底层宠物施法函数在 SP=0 时会立即发送请求，不会替调用方排队等待 SP 变成 1。应由脚本保留“待施法”意图，检测到 SP>0 后尽快发出。
- 方士曾经不曾的“天之箭”技能 ID 为 354、角色学到 7 级。旧代码走通用 `cast_skill` 函数时，发出的 `0x1005` 与玩家手动施法抓包格式不符，因此没有触发。修正后按手动抓包格式构造 `0x1005`，并校验当前客户端指令点特征，再发送。

## 蓄力点与宠物技能

把 SP 看作宠物本场战斗可用的施法机会计数。刷图脚本不要因“刚施法过”就假定 SP 必定归零：

| 施法前后观察 | 含义 | 推荐动作 |
| --- | --- | --- |
| 施法前 SP=0 | 目前没有可用蓄力点 | 继续观察；不要期待客户端自动暂存施法请求 |
| SP 从 0 增至正数 | 获得了可用施法机会 | 尽快发出宠物魔法 |
| 施法完成后 SP=0 | 这次消耗了可用点数 | 等下一次蓄力；无需重发 |
| 施法完成后 SP 仍为原值且大于 0 | 可能触发完美施法，蓄力未被扣除 | 确认宠物行动结束后，立即再施法 |
| 施法完成后 SP 下降但仍大于 0（例如 2→1） | 还有未使用的蓄力机会 | 立即继续施法，不保留这 1 点 |
| 已发指令，但没有行动结束确认且 SP 未变化 | 指令结果仍未确定 | 保持 pending 状态，等行动结束包或 SP 变化；不可按固定短超时盲目重复 |

宠物的施法本身使用客户端 `CastPetMagicToFighter` 路径（仓库 `RVA_CAST_PET_MAGIC`，发出客户端操作码 `0x1004`）。`pet_freecast_patrol.py` 的监测策略是：轮询战斗状态；在宠物存活、敌人存在、MP 达到配置下限且 SP>0 时施放 ID 1504 烈焰爆发；发出后等待宠物行动结束包 `0x4111`（包体首字节与宠物战斗位置相符）或 SP 变化；结束时若 SP 仍为正数就立即继续。轮询间隔 50 ms 是当前脚本设置，不代表服务器每 50 ms 结算一次。

### 完美施法天赋

用户提供的技能提示显示：**完美施法 Lv.10**，描述为宠物在施法结束后有 **20% 概率不扣蓄力点**。这说明“施法成功”和“扣除蓄力”是两个不同结果：宠物可能已经完成一次技能行动，但蓄力仍保留。监测时不能只看是否出现施法/MP 变化，也不能只发一次技能后就假设蓄力已用掉。

这次实战中已经捕获到宠物行动结束后 SP 仍为 1、随后立即再次发烈焰爆发的循环，也观察到蓄力点变化后仍大于 0 时继续施法。20% 是技能说明给出的概率；目前样本不足以独立估算服务端真实触发率或验证不同等级概率曲线。不要把连续几次未扣点当成概率改变，也不要把某一次扣点当成天赋失效。

## 连续施法的判断与执行顺序

1. **处理战斗优先事项。** 先检查是否有队员倒地、队长是否需要本轮救人。若要复活，进入“救援例外”流程，宠物不输出。
2. **确认宠物可行动。** 宠物在战斗中且存活；读到已学的烈焰爆发等级；当前 MP 高于脚本设定门槛；仍有活着的敌方目标。任何条件不满足都不发施法命令。
3. **检查蓄力。** SP=0 时只保留待施法状态并继续监测；检测到 SP>0 才发送施法。不能用 SP=0 的直接请求代替本地待施法队列。
4. **每次只保留一个未决施法。** 发出一次技能后记录当时 SP 和发送时间，等待 `0x4111` 宠物行动结束事件或 SP 变化。没有确认时不要并发追加相同命令。
5. **结算后马上再决策。** 若 SP=0，回到等待；若 SP>0，无论它保持不变还是从 2 降至 1，都立即使用剩余点数再次放技能。战斗结束、宠物死亡、地图/验证状态异常时清除 pending 并停止发包。
6. **设置保护上限和异常日志。** 当前独立巡逻验证脚本限制每场最多 8 次施法，属于保护阀，不是游戏规则。达到上限后本场停止追加；生产循环应按实测场景配置，并记录每次施法前 SP、结束信号、施法后 SP、MP 和结果。

这里的 50 ms 轮询是脚本观察延迟，不是抢在服务器蓄力前施法。若客户端/服务端后来能证明存在可靠的预输入队列，可以再测试队列行为；现有证据不支持把它当作已可用功能。

## 救倒地队员时的例外：宠物防御

输出循环必须让位给救援。队长看到队员倒地并准备使用复活道具时：

1. 队长把复活道具用在倒地队员身上。
2. 宠物本轮下**防御**指令，用防御处理本轮行动/蓄力，不施放烈焰爆发。
3. 队员确认起身后，再恢复普通宠物施法循环。

原因是宠物群攻可能杀掉最后一只怪，让战斗在复活指令生效前结束；曾有实战记录表明队员因此仍倒地并被送回村。仓库 `research/shitu/revive.py` 在队长救援逻辑中先阻断普通输出，并在宠物轮到行动时发 `FIGHT_DEFEND = 4`。即使复活动作已经先发出、宠物稍后才获得行动机会，也要保持防御优先，不能让普通宠物输出抢走这个行动。蓄力点是可用于战斗行动的资源，救援例外下，用户指定应以防御消耗本轮可用点数；救援优先于“剩余 SP>0 就放魔法”的默认规则。

## SP=0 的预约施法实验

在禁锢之地（地图 1200）实测时，宠物 SP=0 下调用仓库直接施法路径，抓到客户端立即发出的 `0x1004` 请求，包体为 `00400040000107000d00e005`。之后 SP 上升至 1、并曾继续变高，但 MP 没有下降，也没有宠物 `0x4111` 行动结束事件；该次请求没有在蓄力变正后执行。结论只覆盖当前 2.101 客户端直接函数调用路径，不证明 UI 按键、其他客户端版本或服务端对其他协议的处理完全相同。

实现上需要区分：**本地待施法标志**（尚无 SP，脚本暂不发送）与**已发送、等待结算的 pending 命令**（已经有 SP 并发包，等行动确认）。SP=0 的直接发包不是有效的预约；它只会形成一次未获执行的请求。

## 方士的天之箭（ID 354）

### 原问题

队长角色职业为方士时，战斗循环仍可能走猎人扫射/普通攻击的通用分支。方士没有扫射，观察到的行为是队长持续普攻，而不是天之箭。角色检测到方士后应锁定天之箭，不得在技能请求失败时悄悄退回普攻；仓库循环应使用指定技能模式，并在错误或未响应时记录/停止，而不是用普攻掩盖配置问题。

此外，问题不只是技能 ID 或等级。对 `CastSkillToFighter` 的 RVA 和参数做直接调用，旧通用 `cast_skill` 路径构造的请求与手动施放天之箭抓到的包格式不同。曾经不曾与波大均为 7 级天之箭；把请求等级改成 1 也没有触发，符合服务端可按角色学到的等级处理请求这一观察，但没有解决封包布局错误。

### 手动包格式与修复

用户手动在波大当前战斗中施放天之箭时，抓到了玩家技能操作码 `0x1005`。当前 2.101 实现按该手动魔法封包布局发送：

```text
<u32 callsite><u16 (target_pos << 8) | 0xF0><u16 0x0106>
<u16 level><u16 skill_id=354><u32 0>
```

`cast_magic_skill_captured()` 目前只允许技能 ID 354，并在发包前检查 `MANUAL_MAGIC_CALLSITE_RVA` 处的客户端字节是否为 `8b178bf0`；特征不匹配就报错停止，避免把 2.101 的抓包布局误用于不同构建。`lunhui15.py` 对配置为天之箭的方士调用此抓包格式路径；猎人扫射仍按它自身已验证的技能路径处理。

### 推荐使用方式与证据边界

- 先按角色职业选技能：方士用天之箭 ID 354；猎人用扫射 ID 803。方士没有可用扫射时不能退回普攻。
- 优先从角色学习技能数据读取等级。当前天之箭学习等级内存读取曾未暴露该技能，因此流程使用用户确认的等级配置（曾经不曾、波大均为 7 级）；发包仍应带配置等级，并记录来源，不要把未读到写成未学习。
- 只在匹配的客户端版本、抓包特征校验通过后使用 `cast_magic_skill_captured()`。如果客户端字节不匹配，停止而不是盲发。
- 成功判断要看服务器/战斗状态的实际响应（技能行动、MP/状态/伤害等），函数返回或“包发出”只证明发送请求，不证明技能成功命中。
- 目前验证的是用户手动释放所对应的魔法包格式及当前构建的 354 路径，不应据此声称所有人物技能或客户端版本都适用同一布局。

## 职业识别：当前能力与建议实现

仓库当前**没有** `read_profession()` 这类直接读取并返回职业名称的接口；`read_world()` 也不含职业字段。已有 `read_skill_level(mem, skill_id)` 能从角色技能向量读取某个技能等级（未学习返回 0，会话未就绪返回 `None`），战斗循环也已经用它检查扫射 803、天之箭 354。因此现在可以先做基于职业标志技能的只读识别，但这属于技能组合推断，不应冒称直接读到了服务端职业字段。

当前已确认、适合作为候选签名的技能：

| 职业 | 候选标志 | 当前证据与限制 |
| --- | --- | --- |
| 猎人 | 扫射 803 | 仓库多个师傅循环使用该技能；可用技能学习等级判断是否已学。若角色尚未学会、技能表未加载或该技能并非职业专属，就不能单凭缺失断定不是猎人。 |
| 方士 | 天之箭 354 | 用户已确认曾经不曾、波大是方士且技能为 7 级；本仓库记录了手动施放抓包与该技能路径。当前客户端技能表读取器曾读不到 354，因此 `0`/`None` 不能直接解释为非方士。 |
| 元素使 | 魔法火焰 206 | 2026-11-05 实测（欧皇丨花花乀、自由三号，通天塔一区）：用户在战斗中按 F1，游戏自己发出的 `0x1005` 是技能 206、12 级；人物发 1504（烈焰爆发）时服务器提示"无此魔法"，1504 只属于宠物。人物的魔法等级不在技能向量里，要从角色数据 +0x1C518 的 `(1, 206, 等级)` 读（`world.read_assist_skill`）。`lunhui15.Caster` 在人物没有扫射和天之箭时，用这个槽里的魔法火焰；两个号各打 2–3 场，人物蓄力点都被正常扣掉。 |

实施时建议先输出三种结果而非强行二选一：`确定`（读到经过验证的职业专属标志，且无冲突）、`候选`（只看到未完成验证的技能证据）、`未知/冲突`（技能未加载、没有签名或同时命中多组）。战斗决策根据确定结果选猎人扫射 803、方士天之箭 354、元素使配置的技能；方士指定 354 但等级读取失败时走用户确认的显式等级配置，且不得退回普攻。

若要做到不依赖角色是否学了特定主动技能，下一步应对 2.101 客户端中角色职业字段做**只读定位**：从当前登录角色/职业面板对应的客户端对象或服务端角色更新包入手，和已知勇者、术士、浪客、学者以及已知猎人、元素使、方士角色交叉比对；确认字段的类型、取值、生命周期和版本签名后，再加入有版本校验的 `read_profession()`。在交叉验证完成前，不硬编码未经确认的职业数值，也不把一转职业名直接猜成二转职业名。

## 证据与限制

- 完美施法 Lv.10、20%不扣点来自用户提供的客户端技能提示；这是提示文字，不是统计过的服务端概率。
- “SP>0 可尝试施法、行动结束后若 SP 仍正就再施法”由当前战斗状态读取、宠物 `0x4111` 行动结束包和多次实战重放观察支持。没有据此断言 SP 的完整生成公式、每个职业/宠物的蓄力周期或服务端全部规则。
- SP=0 的直接施法请求没有排队，是上述一次 live 预输入尝试的结论；测试样本为一次，不外推到 UI 预输入或其他构建。
- 天之箭修复基于手动施放抓包、2.101 客户端调用点特征以及修正后的代码路径。施法等级以用户现场确认的 7 级为准；学习等级读取器在该角色/构建中未能读出 354。
- 相关线上操作和观察日期：2026-11-03。若更换客户端构建，先重新核对包布局、调用点签名和回包行为。

## 2026-11-05：公共 Caster 改用"结算后再放"，以及出手时间线

**代码**：`research/shitu/lunhui15.py` 的 `Caster`（勇者线、元素使线每一场战斗都走它）原来是固定 0.6 秒盲目重发（`91e7959`），已改成和监狱脚本同一套规则：
- 同一时间只挂一个未结算的宠物施法；
- 收到服务器 0x4111（本宠物位置）或蓄力点变化，才算这次出手结算；没有录包的客户端，改看宠物蓝减少，或 3.2 秒兜底；
- 结算后蓄力点 > 0 就立即再放；
- 0x4111 的第二个字节是服务器给的蓄力点，和内存不一致时以服务器为准（实测内存会比服务器晚一拍，曾因此多发一次）。

录包读取器会自动找客户端已加载的 DLL 旁边的 `runtime/tap_<pid>_codec.json`，我们的 DLL 和 Codex BattleAssist 的 DLL 都适用。
测试见 `tests/test_pet_flame.py`。

**实测**（欧皇丨花花乀 6 场，自由三号 6 + 10 + 6 场，通天塔一区，脚本每 0.05 秒轮询一次）：
- 最后一轮 6 场：宠物发了 6 次技能，服务器显示蓄力为 0 时发的 0 次，没结算就又发的 0 次。
- 三轮合计 21 次结算，3 次结算后还剩蓄力点，都立即再放了。
- 次数还少，不能当作完美施法的实际触发率。

**战斗包的含义**（来自时间线，`<u8 pos>` 是战斗位置，人物 17 = 0x11，宠物 12 = 0x0c，怪 0–4）：

| 包 | 方向 | 含义 |
|---|---|---|
| 0x4105 `<pos>` | 服务器 → 客户端 | 这个位置刚得到蓄力点，轮到它下指令 |
| 0x1005 / 0x1004 | 客户端 → 服务器 | 人物 / 宠物 的施法指令 |
| 0x4106 | 服务器 → 客户端 | 这个位置的动作被执行（怪的 0x4105 和 0x4106 在同一毫秒到达：怪的指令由服务器当场决定） |
| 0x4111 `<pos><sp>` | 服务器 → 客户端 | 这个位置的动作结算完毕，以及结算后的蓄力点 |

**时延**：
- 从收到 0x4105 到我们发出指令：人物 40–106 毫秒，宠物 31–92 毫秒。这一段主要花在脚本的 0.05 秒轮询上。
- 从发出指令到服务器执行（0x4106）：约 100–235 毫秒。这一段是网络加服务器处理，我们控制不了。
- 开场蓄力点还是 0 时就发的指令（t≈0.1 秒），服务器直接不理，不存在"预约出手"。
- 自由三号第 3 场：宠物 3.467 秒得到蓄力点，我们 3.516 秒发出指令；3 号、2 号怪比宠物晚得到蓄力点，却和宠物在 3.685 秒同一批被执行，而且排在宠物前面。

### 2026-11-05：轮到就出手（0x4105 触发）+ 战斗中 0.03 秒检查一次

`Caster` 只要读到服务器的 0x4105（"这个位置刚得到蓄力点"）就立即发指令，不等游戏内存里的蓄力点更新。这个位置在 0.6 秒内、或直到它的 0x4111 结算包到达之前，内存读到的 0 不算"已扣点"，避免重复发。开关：`SHITU_TURN_PACKET=0` 关闭，默认打开。

A/B 实测：自由三号，通天塔一区，每组 25 场，两组都是每 0.03 秒检查一次。
