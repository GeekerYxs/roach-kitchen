# 抓宠一级宝宝

这里汇集《什么什么大冒险2》客户端 2.101 的一级宝宝自动巡逻与捕捉代码、实验记录和结论。六角色的线上实验使用本仓库 `batch_provision` 控制桥、战斗内存和客户端函数；本目录中的 `runner.py` 将当时的脚本改为命令行参数形式，**参数化版本尚未在游戏中重跑验证**。原始六角色事件快照与单项实验证据保存在 `证据/`。

## 文件

- `runner.py`：单角色两点巡逻、识别一级目标、逃跑、防御和连续使用捕捉道具；六个角色各运行一个进程。
- `fighters.py`：从战斗结构读取位置、名称、等级、HP、敌我类型，并校验当前构建的函数签名。
- `summarize.py`：离线读取 JSONL 或 JSONL.gz，按运行批次、战斗编号、敌方位置去重。
- `export_evidence.py`：将本机实验日志导出为字段白名单的压缩快照；不会复制原始网络流。
- `decode_tap_evidence.py`：仅提取本次研究中已识别的请求操作码与位置、槽位或动作字段，不导出原始包体。
- `研究记录.md`：协议、实验结果、数据口径和已知限制。
- `证据/数据/`：脱敏冻结快照；`证据/快照汇总.json` 带每个文件的 SHA-256 和各角色汇总；`证据/封包字段摘录.jsonl` 是本次实验的少量已解码字段。
- `证据/历史脚本/`：17 份历史研究脚本的脱敏文本，保留失败尝试和后续改动；路径、进程和角色标识已替换，不能直接运行。

## 运行前

需要 Windows、Python 3.10 以上、仓库中的 `batch_provision`、与偏移相匹配的 2.101 客户端及在地图中的角色。角色必须独立战斗；脚本以角色 ID 查找唯一进程，检查地图、组队状态和道具。`UseItemToFighter` 和 `GetFighterName` 有签名检查，但这些检查并不能替代对客户端版本和运行状态的完整验证。

该程序会真实巡逻、逃跑并消耗道具。一个角色只能由一个控制器操作，开始前应先确认没有其他脚本或游戏自动战斗设置与之冲突。**出战宠物或游戏自动攻击可能伤害宝宝**；本次研究尚未完成对所有角色、宠物和自动战斗设置的隔离验证。

若目标进程尚未接入本仓库的控制 DLL，可传 `--attach`：它会注入 DLL、安装网络 tap，并在本机生成原始网络日志。原始网络日志可能含敏感数据；仓库忽略这些运行文件，提交前仍应人工检查。已有 DLL 且状态为进入世界时不需要此参数。

## 示例

先将示例中的角色 ID 换成实际值。以下是魔力布老虎路线：

```powershell
python -X utf8 .\抓宠一级宝宝\runner.py --role 角色1 --char-id 123456 --map 181 --target 魔力布老虎 --a 3500 2700 --b 3000 2700 --bait-id 8713 --pet-item-id 40146 --attach
```

智者小精灵路线：

```powershell
python -X utf8 .\抓宠一级宝宝\runner.py --role 角色1 --char-id 123456 --map 210 --target 智者小精灵 --a 2576 1891 --b 2181 1942 --bait-id 8713 --pet-item-id 40066 --attach
```

多角色分别运行命令，并为每个角色指定不同标签与角色 ID。两条路线是本次现场使用的坐标，不代表任意客户端或地图条件下都能通行。

停止单角色：在 `抓宠一级宝宝/runtime/` 创建 `<角色标签>.stop`；脚本看到标记后取消寻路并退出。再次启动前，确认旧进程已退出，再删除该标记。运行日志写入同目录 `<角色标签>.jsonl`，不会自动提交。停止脚本时若角色仍在战斗，客户端自己的自动战斗可能继续行动。

## 行为与边界

目标必须同时满足敌方 `type=1`、名称精确匹配、等级 1、HP 大于 0。脚本只对当前锁定的客户端战斗位置调用客户端函数，每次重新核对名称、等级和位置，并重新读取道具槽位；人物蓄力点 ≥3 时优先发送防御动作 7，≥1 时可尝试道具。每场最多 50 次道具请求。

确认没有目标且敌方阵容和等级可读后，发送逃跑；逃跑未结束时继续核对阵容并重试。目标消失不会自动认定捕获成功；若阵容长时间不可读、单场上限、道具耗尽、地图变化或意外战斗结束，脚本可能停止，需看 `runtime` 日志。**一秒稳定快照和 0.1 秒轮询无法证明不会漏读迟到的目标**，不能把观测数据等同服务器完整生成记录。

调用返回值只表示客户端调用已执行，不等于服务器接受或捕获成功。战后新增目标宠物物品结合道具扣除和目标消失，是强支持证据；仍须区分玩家手动转移物品、槽位变化及没有捕捉前快照的情况。紫色外观没有找到可靠的内存字段，不能仅凭等级判断颜色。

## 汇总与验证

```powershell
python -X utf8 .\抓宠一级宝宝\summarize.py --target 魔力布老虎 .\抓宠一级宝宝\证据\数据\six_tiger_伏地魔1.jsonl.gz
python -X utf8 -m unittest discover -s .\抓宠一级宝宝 -p 'test_*.py' -v
```

`summarize.py` 的敌方数量按每次 `started`、场次和位置去重；同一场 `roster` 多次变化不会重复计数。可能抓获要求针对该目标发道具、目标消失，且战后**同一堆叠槽位**可观察到数量下降；槽位变化或耗尽后该格消失时会保守漏算，需要人工核对。`历史长监测` 使用 `monitor_start`、`battle_no` 和 `roster_change`，与六人实时日志字段不同。

## 数据隐私

冻结快照仅保留战斗、位置、道具数量与研究事件白名单，删除 PID、角色 ID、原始包体和进程世界对象；角色标签和游戏内名称仍保留。原始 ETL、PCAP、tap 原包、账户配置、密钥和运行日志不属于本提交。`export_evidence.py` 面向本机原始研究目录，不会覆盖原始文件。
